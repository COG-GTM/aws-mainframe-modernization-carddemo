# What this harness does not prove

A passing reconciliation - "N records, M fields reconciled, 0 differences" -
is a precise statement with narrow scope.  These are the limits, stated so
that the number is not read as more than it is.

## 1. GnuCOBOL on ASCII/Linux is not Enterprise COBOL on z/OS

The golden outputs were produced by `cobc (GnuCOBOL) 3.1.2.0` compiling the
unmodified source with `-std=ibm -fsign=EBCDIC` (`expected/run.json`).  The
harness therefore establishes that *the candidate agrees with GnuCOBOL's
execution of the program*.  Places where GnuCOBOL and Enterprise COBOL are
known or plausible to differ, none of which the harness can detect:

* **Character encoding and collation.**  All data is ASCII.  Comparisons such as
  `ACCT-EXPIRAION-DATE >= DALYTRAN-ORIG-TS (1:10)` (`app/cbl/CBTRN02C.cbl:414`)
  happen to agree for digits and `-`, but any field containing letters, spaces
  and punctuation collates differently in EBCDIC.  Indexed-file key order
  (`TRANSACT` by `TRAN-ID`, `TCATBALF` by `TRAN-CAT-KEY`) is ASCII order here.
* **Sign representation.**  `-fsign=EBCDIC` reproduces the mainframe overpunch
  characters, but the runtime that *reads* them is still GnuCOBOL.  Packed
  decimal (`COMP-3`) fields are absent from these layouts, so nothing is proved
  about them.
* **Arithmetic overflow and truncation.**  No `ON SIZE ERROR` is coded on
  `ADD DALYTRAN-AMT TO TRAN-CAT-BAL` (`:527`) or the account adds (`:547-552`).
  Truncation on overflow is compiler-defined; the generator keeps totals in
  range, so this is untested on either side.
* **File status codes and VSAM semantics.**  GnuCOBOL's Berkeley DB indexed
  files return status `23` for a missing key like VSAM does (`:481` relies on
  that), but duplicate-key, locking, `OPEN` on an empty cluster, and
  `REWRITE INVALID KEY` (`:554-559`) behaviours are not exercised.
* **Runtime services.**  `CALL 'CEE3ABD'` (`:711`) is Language Environment; a
  GnuCOBOL run would fail differently on an abend path.  No golden set reaches
  it.
* **`FUNCTION CURRENT-DATE` precision** is frozen by `COB_CURRENT_DATE`; the
  live precision and time zone of the two platforms are not compared.

A golden set produced *on the mainframe* from the same inputs would close these
gaps for the cases it contains (see `government-decisions.md`, row 3).

## 2. Synthetic data is not production data

Every record was generated by `tests/golden/generate.py` from a seed.  Card
numbers fail the Luhn check, ids carry a `9000` prefix, names are labelled
`GOLDEN`.  Consequences:

* The distribution of amounts, type/category codes, accounts per card and
  transactions per account is the generator's, not the feed's
  (`manifest.json` -> `volume_mix_percent`).
* Field contents that production populates and the generator does not vary
  (`TRAN-SOURCE`, `TRAN-DESC` wording, merchant zip formats, `ACCT-GROUP-ID`,
  status flags) cannot reveal a candidate defect in how they are carried.
* Production-only anomalies - malformed records, non-numeric bytes in a
  numeric field, duplicate `TRAN-ID`s within a day, a `DALYTRAN` file that is
  empty - are not present.  What the original program does with them is
  therefore also undocumented here.

## 3. A golden set proves equivalence on the cases it contains, and nothing else

19 named behaviours and a 1,200-record mix were compared.  The comparator
reports zero differences on those.  It says nothing about:

* branches no case reaches (reason `109`, abends, category overflow -
  `findings.md` 2.7, 2.9);
* combinations not generated (for example an expired account whose card is also
  missing - impossible by construction, since the card lookup short-circuits,
  `:372-376`; or three or more transactions on one account in one run);
* any input volume or key-range effect beyond 1,200 records;
* performance, resource use, restartability, or behaviour when a file is
  missing or locked.

Adding a case is cheap (`generate.py` `@case`), and the reconciliation report
is only ever as strong as the case list.  Which cases must be present is a
system-owner decision (`government-decisions.md`, row 1).

## 4. The comparator has scope too

* It compares the four record files, `RETURN-CODE`, and `SYSOUT`.  It does not
  look at anything the candidate might write elsewhere (its own logs, a
  database, metrics).
* `SYSOUT` is compared as informational; a difference there does not change
  the verdict.  Whether that is acceptable is row 9 of
  `government-decisions.md`.
* Field splitting uses the copybooks as parsed by `tests/golden/layouts.py`.
  A copybook construct the parser does not understand (`REDEFINES`, `OCCURS`
  with `DEPENDING ON`, level-88 conditions used as data) would be reported at
  parse time, not silently mis-split; none occur in the six layouts used.
* Self-test coverage is the nine mutant classes in `tests/golden/mutate.py`.
  A defect class outside them (for example a candidate that writes a correct
  file to the wrong ddname) is caught only indirectly, as a missing or empty
  file.

## 5. VSAM under CICS is out of scope

`CBTRN02C` is a batch program run by `POSTTRAN.jcl`.  The online programs that
read and update the same VSAM clusters through CICS (record locking, enqueue
behaviour, concurrent update of `ACCTFILE` and `TCATBALF` while the batch
posts, syncpoint and backout) are not part of this cycle and are not
exercised.  The golden sets assume the batch run has exclusive access to its
files, which is what the JCL's `DISP=SHR` (`app/jcl/POSTTRAN.jcl:28-42`) does
*not* by itself guarantee on the mainframe.

## 6. The candidate run has its own caveats

The pull request #9 candidate was built and executed once per set in this
environment (JDK 21, Maven with a repository mirror, `faketime` for the clock,
its own unit tests skipped).  The comparison shows what that binary produced
from these inputs on this machine; it is not a statement about the candidate's
behaviour under its intended runtime, scheduler, or data source, nor about any
commit other than `03912525cf8bf90b8e810b2616f67c99a77d0abd`.
