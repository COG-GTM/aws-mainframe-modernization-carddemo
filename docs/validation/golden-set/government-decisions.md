# Decisions only the system owner can make

The harness in `tests/golden/` is a measuring instrument.  What it measures,
against what, and how many times before the result counts as evidence are
policy questions.  None of them is decided here; each row records what the
instrument can show, what happens if nobody decides, and who plausibly owns the
call.  "Evidence" points at the artefact in this repository that the decision
would act on.

| # | Decision | Evidence available today | Consequence of not deciding | Plausible owner |
|---:|---|---|---|---|
| 1 | **Which production-shaped cases must be in the golden set.**  The committed sets contain 19 named behaviours (`tests/golden/sets/named/input/manifest.json` -> `cases`) chosen by reading the program, plus a 1,200-record mix at a ratio the generator documents (`manifest.json` -> `volume_mix_percent`).  Nobody has confirmed that these are the shapes production actually sends (amount distribution, type/category mix, share of multi-transaction accounts, reject rate). | `findings.md` section 2 lists the behaviours found in the code; `expected/prediction-check.json` shows the reject mix of the volume set (49 / 33 / 52 / 19 by reason). | The gate proves equivalence on the cases we guessed.  A converted program can pass and still differ on a shape production sends every day (for example a type/category code the generator never emits). | Business owner of the posting cycle, with the operations team that sees the daily feed |
| 2 | **Tolerance policy.**  `compare.py` accepts no difference by default; `--tolerance FIELD=ABS` is the only escape and is printed in the report.  Whether any field may ever differ (`TRAN-PROC-TS`?  `SYSOUT` wording?) is a policy choice. | `compare.py` `--tolerance` flag; reconciliation reports carry a "Tolerance policy in effect" banner when used.  `SYSOUT` is already compared as informational only, which is itself an undecided tolerance. | Every run either fails on a clock difference nobody cares about, or someone adds a tolerance locally and the reports stop being comparable across runs. | System owner, signed off by whoever signs row 5 |
| 3 | **Golden source: mainframe or GnuCOBOL.**  The committed golden outputs come from GnuCOBOL 3.1.2 on ASCII/Linux running the unmodified source.  That proves the candidate matches *GnuCOBOL's* reading of the program.  It does not prove GnuCOBOL matches Enterprise COBOL on z/OS (EBCDIC collating, sign nibbles, overflow truncation, VSAM status codes).  A mainframe-produced golden set would close that gap for the cases it contains. | `expected/run.json` records the compiler and the exact `cobc` command; `what-this-does-not-prove.md` lists the known dialect gaps; `findings.md` 2.9 and 3.4 name the fields most exposed. | Cutover evidence rests on an emulator.  If a dialect difference exists in a field that matters, both reference and candidate can agree with each other and disagree with production. | System owner together with the mainframe operations group that can run `POSTTRAN.jcl` against copied, sanitised data |
| 4 | **How many parallel cycles must reconcile before cutover, and on what data.**  One run per set is committed here.  A production gate typically wants N consecutive daily cycles on real (or masked real) feeds with zero unexplained differences. | `compare.py` produces one `reconciliation.json` per cycle; the JSON has stable keys so N runs can be aggregated. | "It passed once on synthetic data" becomes the de-facto criterion by omission. | Programme / release authority for the posting system |
| 5 | **Who signs the reconciliation report, and what a signature means.**  `reconciliation.md` is generated; nobody is named in it. | Report header fields (`expected`, `candidate`, `verdict`, tolerances) are all present for a sign-off block to reference. | Reports accumulate without accountability; a later question "who accepted this difference?" has no answer. | System owner (accountable) with an independent reviewer who did not build the candidate |
| 6 | **Retention of golden sets and reports as evidence.**  Inputs, expected outputs and reports are committed to this repository today.  How long they must be kept, where (repository vs. records system), and whether the toolchain (GnuCOBOL 3.1.2, JDK 21) must be preserved to re-run them are open. | `run.json` and `env.txt` capture the toolchain; sets are small (about 3 MB for both sets together). | Evidence exists only as long as the branch does; a future audit cannot re-execute the comparison. | Records / compliance function for the system, advised by the owner |
| 7 | **What the candidate's `RETURN-CODE 0` means for the job stream.**  The original returns `4` when any reject was written (`app/cbl/CBTRN02C.cbl:229-231`); downstream JCL may condition on it.  The comparator treats a return-code difference as a mismatch.  Whether the converted job stream is allowed to signal rejects differently is a decision, not a defect finding. | `candidate-pr9/*/reconciliation.md` (`RETURN-CODE` row); `app/jcl/POSTTRAN.jcl` has no `COND=` on this step, so the consumer of the code is outside the visible repository. | Either the candidate is held to a code nobody consumes, or a code that something *does* consume is silently dropped. | Owner of the batch schedule that runs `POSTTRAN` |
| 8 | **Handling of the paths the program can take but no golden set exercises** (reason `109` after a failed `REWRITE`, `findings.md` 2.7; abends via `CEE3ABD` at `:707-711` on file errors; category-balance overflow, `findings.md` 2.9). | Cited in `findings.md`; not represented in any set. | The converted program's behaviour on operational failure is unverified and may never be, because the reference cannot easily be driven there. | System owner, with operations |
| 9 | **Treatment of `SYSOUT`.**  The program's `DISPLAY` output (counts, `Creating.` lines) is captured and compared as informational.  Whether it is part of the interface (operators or automation read it) or free text is undecided. | `expected/SYSOUT`; `compare.py` reports `SYSOUT differs (informational)`. | Operators' runbooks may depend on lines the candidate does not emit; or the gate fails on cosmetic wording forever. | Operations lead for the batch window |

No row above is decided by this pull request.  Rows 1, 3 and 4 determine whether
the numbers in `README.md` can be called cutover evidence at all; the remaining
rows determine what a passing report is worth once they are.
