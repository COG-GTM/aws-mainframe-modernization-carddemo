# Open questions (CBTRN04C)

The repository has no requirements document for the daily feed, so the points
below were inferred from copybooks, `CBTRN02C`, the JCL and the sample data. Each
is implemented conservatively and marked **Inferred — needs owner confirmation**
in `change-request.md` where it corresponds to a rule.

| # | Inferred | Basis in the repository | What was implemented |
|---|----------|-------------------------|----------------------|
| 1 | `DALYTRAN-ID` must be populated (R01) | `CVTRA06Y.cpy:5` gives `PIC X(16)`; nothing in the repository checks or generates it, and `CBTRN02C` copies it into the transaction master key without a check | Reject when all spaces or all LOW-VALUES; any other content accepted (no format rule) |
| 2 | Transaction type must exist in `TRANTYPE` (R02) | The file and its layout exist (`CVTRA03Y.cpy:5`) but `CBTRN02C` never reads it | Reject on `INVALID KEY` (status 23) |
| 3 | Category is validated as type + category, not alone (R03) | `TRANCATG` is keyed on `TRAN-CAT-KEY` = type + category (`CVTRA04Y.cpy:5`-`7`); there is no category-only key or file, and posting keys `TCATBALF` on the same pair (`CBTRN02C.cbl:506`) | One keyed read of `TRANCATG` on the pair; a category valid under another type is a reject |
| 4 | Sign convention of the amount field | `PIC S9(09)V99` zoned decimal (`CVTRA06Y.cpy:10`); the ASCII sample data carries EBCDIC-style overpunched signs (`{`, `A`-`I`, `}`, `J`-`R`) | NUMERIC class test; GnuCOBOL tests compile with `-fsign=EBCDIC` so the sample data reads as it would on the mainframe |
| 5 | Amount range is checked against the projected category balance (R07) | Narrowest downstream field is `S9(09)V99` (`CVTRA01Y.cpy:9`, `CVTRA05Y.cpy:10`); `CBTRN02C` adds without `SIZE ERROR` (`CBTRN02C.cbl:508`, `:527`, `:547`); `ACCT-CURR-BAL` is wider (`CVACT01Y.cpy:7`) | Read `TCATBALF` by account + type + category once per key, add the amount in `COMP-3`, reject when outside ±999,999,999.99; each accepted amount advances an in-storage projection for its key so a second record for the same key is checked against the balance the first one will leave (`CBTRN02C` rewrites `TRAN-CAT-BAL` after every posting, `CBTRN02C.cbl:527`). Missing balance record = 0 (as `CBTRN02C` creates it). `ACCT-CURR-BAL` (`S9(10)V99`) is not range-checked: it is wider than the feed amount and `CBTRN02C` has no ceiling test on it; the account cycle credit/debit are projected for the credit-limit rule (R13) |
| 6 | Timestamp text format is `YYYY-MM-DD hh:mm:ss.ffffff` (R08, R09) | `CBTRN02C.cbl:414` compares `DALYTRAN-ORIG-TS (1:10)` with `ACCT-EXPIRAION-DATE PIC X(10)`; `Z-GET-DB2-FORMAT-TIMESTAMP` builds the same shape | Only bytes 1-10 are validated; the time portion is not checked |
| 7 | Whether a blank processing timestamp is valid (R09, R10) | All 300 sample records have a blank `DALYTRAN-PROC-TS`; `CBTRN02C.cbl:438` overwrites it at posting | Blank accepted; R09/R10 and the R11 processing-date check apply only when present |
| 8 | Run-date `PARM` format is `YYYYMMDD` and dates after it are rejected (R11) | `INTCALC.jcl:22` passes `PARM='2022071800'` to `CBACT04C`, whose `PARM-DATE` is `PIC X(10)` (`CBACT04C.cbl:178`); the tasking asks for `YYYYMMDD` | Exactly 8 numeric bytes, validated as a Gregorian date, else RC 8 before any file is opened; "after" means calendar date only |
| 9 | How the `PARM` reaches the program | `CBACT04C` receives it through `PROCEDURE DIVISION USING` linkage, which GnuCOBOL does not allow in a main program built with `-x` | `CALL 'CEE3PRM'` (Language Environment) with `ON EXCEPTION`; `tests/cbtrn04c/stubs/CEE3PRM.cbl` supplies it under GnuCOBOL from `CBTRN04C_PARM` |
| 10 | Reason-code numbering for the new rules | `CBTRN02C` uses 100-103 (`CBTRN02C.cbl:385`, `:397`, `:410`, `:417`) | `0100`-`0103` reused with the same text for the card and account checks (R05, R06, R12, R13); `0201`-`0210` for new rules |
| 11 | Return code for file errors | `CBTRN02C` abends via `CEE3ABD` (`CBTRN02C.cbl:707`) rather than setting a return code | RC 12, so the `COND` on `POSTTRN2.jcl` can test it; an abend would also skip the posting step |
| 12 | Rejected amounts that are not numeric cannot be totalled | A non-numeric zoned field has no defined value | Counted on a separate report line and excluded from the accepted, rejected and total amounts so the reconciliation is exact |
| 13 | The Julian range on the report covers origination dates only | The tasking asks for "the Julian range of accepted transactions"; processing timestamps may be blank | Min/max of accepted origination dates in `YYYYDDD`; `NONE` when nothing was accepted |
| 14 | Data set names and high-level qualifier in the new JCL | The new jobs cannot be executed in this environment | `SET HLQ=SITE.HLQ` placeholder; set to the qualifier used by `POSTTRAN.jcl` at implementation |
| 15 | Report destination | `CBTRN02C` writes only `DISPLAY` lines to `SYSOUT` | Separate `VALDRPT` DD, `RECFM=F LRECL=133`, routed to `SYSOUT=*` in the JCL; `DISPLAY` totals also go to `SYSOUT` as in `CBTRN02C` |
| 16 | Number of distinct account/type/category keys and distinct accounts one daily feed can carry | No feed volume is documented; the sample feed has 300 records over 50 accounts | Each projection table (`WS-BAL-TABLE`, `WS-ACCT-TABLE`; `CBTRN04C.cbl:345`, `:368`) holds 20,000 keys, searched serially; a feed with more distinct keys ends with RC 12 and a message rather than validating the excess against a stale balance. Raise the `MAX` value and the `OCCURS` together if the production feed is larger (Government decision 11) |
| 17 | Whether the posting-time account checks of `CBTRN02C` (account exists, credit limit, expiration; `CBTRN02C.cbl:393`-`:420`) belong in the validator | The tasking's stated purpose is that operations can stop the cycle before the master files are touched; `CBTRN02C` rejects on these three conditions after it has started updating masters for earlier records | Implemented as R06, R12 and R13 with the same codes and texts (0101-0103) and a per-account projection of the cycle credit/debit so a second transaction on one account is tested against the balance the first one will leave; `CBTRN02C` is unchanged and still performs its own checks (Government decision 9) |
| 18 | Order of the two account checks when both fail | `CBTRN02C.cbl:403`-`:417` evaluates the credit limit first and then the expiration date without an `ELSE`, so the later `MOVE 103` overwrites 102 and posting reports 103 | R12 (expiration, 0103) runs before R13 (credit limit, 0102) so a record failing both gets 0103 in both programs (`precedence_expired_and_overlimit`) |
| 19 | Whether the expiration compare should run on the raw origination field as `CBTRN02C` does | `CBTRN02C.cbl:414` compares `ACCT-EXPIRAION-DATE` with the raw `DALYTRAN-ORIG-TS (1:10)`; when that field is not a date the result depends on the collating sequence (letters sort below digits in EBCDIC and above them in ASCII) | R12 runs after R08 has proven the origination date valid, so both operands are `YYYY-MM-DD` digit strings and the character compare is chronological in either sequence; a non-date origination is a 0206 reject in both environments (`rule08_orig_not_numeric`) |
| 20 | Sign convention of `ACCT-CURR-CYC-DEBIT` in the credit-limit arithmetic | `CBTRN02C.cbl:549`-`:551` add negative amounts to the debit field and compute `CREDIT - DEBIT + AMT` (`:403`), so the debit field carries a negative value and the subtraction adds it back | The projection follows the same arithmetic and the same update rule (`CBTRN04C.cbl:1165`, `:1256`); the test account master seeds `ACCT-CURR-CYC-DEBIT` negative (`tests/cbtrn04c/refdata/standard/acctdata.txt`) |
| 21 | Whether the 38 sample-feed rejects (0102) are expected | `app/data/ASCII/acctdata.txt` limits versus `dailytran.txt` amounts; `CBTRN02C` would reject the same 38 at posting time | Reported as found (`sample_data`, RC 4); Government decision 12 |
| 22 | Whether `CBTRN02C`'s `WS-TEMP-BAL` `S9(09)V99` (`CBTRN02C.cbl:187`) is deliberately narrower than the `S9(10)V99` account fields it is computed from (`CVACT01Y.cpy:7`, `:13`, `:14`), and whether the account master is ever expected near those limits | `CBTRN02C.cbl:403` computes into it and `:547`-`:551` add to the account fields, all without `ON SIZE ERROR`, so a value beyond the picture is truncated silently | R14 (reason 0210) rejects any record whose projected limit-test value leaves `S9(09)V99` or whose projected `ACCT-CURR-BAL`, `ACCT-CURR-CYC-CREDIT` or `ACCT-CURR-CYC-DEBIT` leaves `S9(10)V99`, using the same per-account projection as R13 (`CBTRN04C.cbl:1185`, `:1021`); Government decision 13 |
