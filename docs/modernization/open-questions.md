# Open questions

Each entry is an ambiguity found in the source. None has been resolved by inventing a rule; the
Java reproduces the source behaviour (or, where impossible, the deviation is named) and the
decision is left to the customer. Ordered by impact on the modernized system, highest first.

| ID | Question | Code reference | What the Java does today |
|---|---|---|---|
| **OQ-04** | `ACCT-CURR-CYC-DEBIT` receives negative amounts *as negative* (`ADD DALYTRAN-AMT` with `AMT < 0`). The over-limit test is `CREDIT - DEBIT + AMT <= LIMIT`, so every posted debit *increases* headroom. Is the debit bucket meant to be a positive magnitude (and the formula `CREDIT + DEBIT`), or is the sign convention intentional? This changes which transactions are rejected. | `CBTRN02C.cbl` 403-407, 548-552 | Reproduces the source: debit bucket goes negative, headroom grows. Tested by `negativeDebitAlwaysPassesTheCreditCheck`. |
| **OQ-17** | In the report loop, an out-of-range record executes `NEXT SENTENCE`, whose target is the period after `END-PERFORM.` — the loop terminates, files close, and no page/grand totals are written. The SORT step normally pre-filters so this branch is not hit, but the two date ranges are independent (OQ-15). Is the intent "skip the record" (probable) or "stop"? | `CBTRN03C.cbl` 173-178, 213; `TRANREPT.jcl` 43-48 | `OutOfRangePolicy.STOP_LIKE_COBOL` is the default; `SKIP_RECORD` is available by configuration. |
| **OQ-18 / OQ-19** | At EOF the program adds `TRAN-AMT` to the page and account totals once more (the record area still holds the last record on Enterprise COBOL; formally undefined after an EOF read), so the last amount is double-counted in the page total and hence the grand total. It also never writes an account-total line for the last card. Are the production reports known to be off by the last transaction, or is this compensated elsewhere? | `CBTRN03C.cbl` 198-206, 306-316 | Reproduces both (`singleRecordRunCountsTheLastAmountTwice…`, `…NeverForTheLastCard`). |
| OQ-01 | The brief describes POSTTRAN → INTCALC → TRANREPT as one daily scheduler cycle. The repo's CA-7 export has POSTTRAN (triggered by CBPAUP0J, triggers WAITSTEP) but no INTCALC/TRANREPT; the Control-M export has INTCALC as *monthly* (folder `MONTHLY-InterestCalculation`) feeding COMBTRAN, and no TRANREPT. What is the real cadence and ordering? | `CardDemo.ca7` 69-97; `CardDemo.controlm` 69-83 | Three independent jobs; no orchestration assumed. |
| OQ-02 | `TRANFILE` (TRANSACT.VSAM.KSDS) is opened `OUTPUT`, which empties a REUSE cluster (or fails on a non-REUSE one with existing records). So the transaction master holds only the current day's postings, and TRANREPT's REPRO/SORT of it can only ever see one day. Intended? | `CBTRN02C.cbl` 254-272; `TRANFILE.jcl` DEFINE | Posting starts from an empty master each run. |
| OQ-03 | `WS-TEMP-BAL` is `S9(09)V99` while its operands are `S9(10)V99`; `COMPUTE` without `ON SIZE ERROR` truncates the high-order digit. An exposure of 1 000 000 050.00 is compared as 50.00. Bug or irrelevant at real limits? | `CBTRN02C.cbl` 79, 403-405 | Reproduced (`wsTempBalIsNarrowerThanItsOperands…`). |
| OQ-06 | `REWRITE` of the account with `INVALID KEY` sets reason 109 but the transaction has already been accepted; it is still written to TRANSACT and the account update is lost, silently. Should a failed account rewrite reject or abend? | `CBTRN02C.cbl` 554-560, 211-216 | Logs a WARN, continues like the COBOL. |
| OQ-07 | No unit of work in any of the three programs. An abend mid-file leaves ACCTDATA/TCATBALF partially updated and SYSTRAN/TRANSACT partially written; a rerun re-applies the first part. What is the operational restart procedure (restore from TRANBKP? rerun from scratch?) | all three `9999-ABEND-PROGRAM` paragraphs | Same: no compensation. Spring Batch records the failure but does not roll back file writes. |
| OQ-12 | With an empty TCATBALF, CBACT04C's EOF branch performs `1050-UPDATE-ACCOUNT` on an `ACCOUNT-RECORD` that was never read (`WS-FIRST-TIME='Y'`). Result on z/OS depends on storage contents (likely abend on REWRITE, possibly corrupt an account). | `CBACT04C.cbl` 221-222, 350-371 | **Deviation:** empty input is a no-op. Only intentional deviation in the implementation. |
| OQ-08 | `ALTERNATE RECORD KEY IS FD-XREF-ACCT-ID` has no `WITH DUPLICATES`, but the AIX is defined `NONUNIQUEKEY` in `XREFFILE.jcl`. Enterprise COBOL accepts the mismatch at run time only if the AIX definition matches; and the program always takes the *first* card for an account. For multi-card accounts, is posting all interest to the lowest card number correct? | `CBACT04C.cbl` 34-39, 393-413 | Uses min card number. |
| OQ-09 | `PARM='2022071800'` is 10 chars, only ever used as the transaction-ID prefix. Is it `YYYYMMDDHH`, a business date + `00`, or a run sequence? Interest transaction IDs are `PARM ‖ 000001…`, so two runs with the same PARM collide in COMBTRAN downstream. | `INTCALC.jcl` 22; `CBACT04C.cbl` 176-178, 474-479 | Treated as an opaque 10-char prefix. |
| OQ-10 | `WS-TRANID-SUFFIX PIC 9(06)` wraps at 999 999 interest rows per run. Real volumes? | `CBACT04C.cbl` 173, 474 | Same width; wraps identically. |
| OQ-11 | `MOVE '05' TO TRAN-CAT-CD` (alphanumeric literal to `9(04)`). Standard rule gives 0005; confirm against a real SYSTRAN record. | OQ-15 | Two date windows: SORT hard-codes 2022-01-01..2022-07-06; CBTRN03C reads DATEPARM (not in repo). Which is authoritative and how are they kept in sync? | `TRANREPT.jcl` 43-44; `CBTRN03C.cbl` 220-247 | Both configurable; SORT window defaults to the JCL literals. |
