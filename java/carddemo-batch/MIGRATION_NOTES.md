# CBACT01C → Java 17 migration notes

Source: `app/cbl/CBACT01C.cbl` (430 lines, with `CVACT01Y` and `CODATECN` copybooks). Target: `java/carddemo-batch/`
(`com.carddemo.batch`, Java 17, Maven, JUnit 5, Gson for reading the goldens; no frameworks).
Parity is proven against `golden-files/CBACT01C/` (sample data, 50 accounts) and
`golden-files/CBACT01C/synthetic-mixed-debit/` (5 accounts with non-zero cycle debits) at four levels:
field by field (JSON), byte for byte (`raw/`), DISPLAY text, and the 29 reconciliation checks of
`test-harness/RECONCILIATION_CHECKS.md` (re-implemented in Java *and* re-run through `test-harness/reconcile.py`).

Build and test: `JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 mvn -B verify` (74 `@Test` methods).
Run (from the repository root, paths are relative to the working directory):
`java -jar java/carddemo-batch/target/carddemo-batch-0.1.0-SNAPSHOT.jar [ACCTFILE OUTFILE ARRYFILE VBRCFILE]`
(defaults: `app/data/ASCII/acctdata.txt` → `OUTFILE`, `ARRYFILE`, `VBRCFILE` in the current directory).

## Layout of the port

| COBOL | Java |
|---|---|
| `CVACT01Y` `ACCOUNT-RECORD` (300) | `record.AccountRecord` |
| `OUT-ACCT-REC` (107, FD OUTFILE) | `record.OutAcctRec` |
| `ARR-ARRAY-REC` (110, FD ARRYFILE, `OCCURS 5`) | `record.ArrArrayRec` (+ inner `ArrAcctBal`) |
| `VBRC-REC1` (12) / `VBRC-REC2` (39) | `record.VbrcRec1` / `record.VbrcRec2` |
| `CODATECN-REC` (80, COBDATFT parameter block) | `record.CodatecnRec` |
| PIC / USAGE codecs | `codec.FixedWidth`, `codec.ZonedDecimal`, `codec.PackedDecimal`, `codec.Layout`, `codec.Field` |
| SELECT … ORGANIZATION INDEXED / SEQUENTIAL | `io.KsdsFile`, `io.FixedRecordWriter`, `io.VariableRecordWriter`, `io.RecordPrefix` |
| FILE STATUS / `CEE3ABD` | `io.FileStatusException`, `io.AbendException` |
| `CALL 'COBDATFT'` | `program.CobDatFt` |
| PROCEDURE DIVISION | `program.Cbact01c` (one method per paragraph, same names: `acctfileOpen` = `0000-ACCTFILE-OPEN`, `acctfileGetNext` = `1000-ACCTFILE-GET-NEXT`, `displayAcctRecord`, `populAcctRecord`, `writeAcctRecord`, `populArrayRecord`, `writeArryRecord`, `populVbrcRecord`, `writeVb1Record`, `writeVb2Record`, `acctfileClose`, `abendProgram`, `displayIoStatus`) |

## Translation decisions

| # | COBOL construct | Java equivalent | Why | Risk |
|---|---|---|---|---|
| 1 | Record = contiguous storage; `MOVE`s between group items are byte copies | Every record class extends `FixedWidthRecord` and *owns a `byte[]`*; typed getters/setters decode/encode in place (`FixedWidth.text/decimal/setText/setDecimal`). `encode()` returns the buffer, so WRITE is a byte copy exactly as in COBOL. | Field-by-field POJOs would re-derive bytes from Java values and lose anything the program never assigns (see #14) or that is not a valid value. Storage-backed records give byte parity for free. | None for parity; slightly unusual API for Java readers. |
| 2 | `PIC X(n)` | `String` of exactly `n` chars, ISO-8859-1, trailing spaces kept; setter space-pads / truncates to `n` like a MOVE | `PIC X` has no "length"; trimming would change the written bytes and the goldens keep trailing spaces (`"20250520  "`). ISO-8859-1 maps each byte to one char so even non-text bytes survive a `String` round trip. | Callers must not `trim()`. The 10-char dates are text, never parsed. |
| 3 | `PIC S9(10)V99` DISPLAY (zoned, sign over-punched on the last byte) | `BigDecimal` with scale 2 via `ZonedDecimal`. Decode accepts the ASCII over-punch set used by the sample data and the goldens: `{`=+0, `A`–`I`=+1..+9, `}`=−0, `J`–`R`=−1..−9, plus GnuCOBOL's native `p`–`y` negatives and a plain digit (unsigned/initialised). Encode always writes `{`/`A`–`I` or `}`/`J`–`R`; zero is `+0` (`…{`). High-order digits are truncated, decimals truncated (not rounded), as a MOVE does. | `double` cannot represent 0.01 exactly; `BigDecimal.compareTo` + `scale()` is the parity contract. The ASCII sample data uses the EBCDIC-style over-punch characters, so the ASCII bytes are what z/OS would show after a code-page translation. | Spaces in a numeric field are rejected (`CodecException`) rather than read as zero as some compilers do; the sample data has none. Negative zero (`}`) decodes to `0.00` and re-encodes as `{` — a round trip of a `−0` would change one byte (not present in the data). |
| 4 | `PIC S9(10)V99 COMP-3` (`OUT-ACCT-CURR-CYC-DEBIT`, `ARR-ACCT-CURR-CYC-DEBIT`) | `PackedDecimal`: 7 bytes = 13 digit nibbles + sign nibble, of which the PIC uses 12 (the spare high nibble is always 0); encode writes `C` (+) / `D` (−), decode also accepts `F` (unsigned); any other sign nibble or a digit nibble > 9 is a `CodecException`. | Explicit codec rather than a library so the sign-nibble rules are visible and testable. `C`/`D` are what GnuCOBOL (and IBM) write for a signed item. | Values wider than the PIC are truncated to its 12 digits high-order first, like a MOVE without `ON SIZE ERROR` (`10000000000.00` → `0.00`). |
| 5 | `PIC 9(11)` (account ids) | `long` getters/setters, zoned unsigned codec (`Layout.unsigned`) | Ids are numeric in the copybook and displayed with leading zeros (`00000000001`); the goldens render them as `"1"`. Keeping the field numeric preserves both. | Key ordering is by the 11 ASCII digits (= numeric order because the field is fixed width and zero padded). |
| 6 | `OCCURS 5 TIMES` (`ARR-ACCT-BAL`) | `Layout.group(name, 5, …)`; `ArrArrayRec.arrAcctBal()` returns a fixed `ArrAcctBal[5]` of views over the record bytes, `arrAcctBal(int occurrence)` is **1-based** like COBOL subscripts; `Field.occurrence(i)` relocates the group and its children by `i × 19` bytes | A `List` would invite add/remove; the COBOL table is fixed. Views keep the single-buffer model (#1). 1-based accessors keep the Java readable against the COBOL (`ARR-ACCT-CURR-BAL(3)` ↔ `arrAcctBal(3).arrAcctCurrBal()`). | Mixed indexing conventions (0-based `Field.occurrence`, 1-based record accessor) — documented on both methods and asserted in `FixedWidthRecordTest`. |
| 7 | `FD VBRC-FILE RECORD IS VARYING … DEPENDING ON WS-RECD-LEN`; `MOVE VBRC-RECn TO VBR-REC(1:WS-RECD-LEN)`; `WRITE VBR-REC` | `VariableRecordWriter.write(recordArea, length)` with lengths 12 and 39 set in `writeVb1Record` / `writeVb2Record`; an 80-byte `vbrRec` area is kept so the reference-modified MOVE is literal. `RecordPrefix` chooses how the record is framed on disk: `GNUCOBOL_VARSEQ` (4-byte big-endian length, what the goldens contain), `ZOS_RDW` (2-byte length + 2 zero bytes, length includes the RDW), or `NONE` (payload only). | On z/OS the access method adds/strips the RDW, so the *program* only ever sees 12 and 39 bytes. The golden `raw/VBRCFILE` was produced by GnuCOBOL with `COB_VARSEQ_FORMAT=1`, so its prefix is a 4-byte length, not an RDW. Making the prefix a parameter keeps the COBOL-visible lengths exact and lets the byte test target the golden. | Anyone comparing against a real z/OS VB dataset must use `ZOS_RDW` (and the file would also carry a BDW per block, which no program-level writer can reproduce). |
| 8 | `SELECT ACCTFILE … ORGANIZATION IS INDEXED, ACCESS SEQUENTIAL, RECORD KEY ACCT-ID` | `KsdsFile`: loads the fixed-width file (300 bytes per record, optional `\n` terminator as in `app/data/ASCII/acctdata.txt`), indexes it in a `TreeMap` on the key bytes; `readNext()` returns records in ascending key order; `read(key)` is available for the random READs of later programs (CBTRN01C). | A VSAM KSDS is read in key order regardless of load order; the sample file is already sorted, but relying on that would make the port depend on an accident. | Whole file in memory (fine for batch sizes here; 50–50 000 records). Duplicate keys → status `22` at OPEN rather than at load time (IDCAMS REPRO would have rejected them). |
| 9 | `FILE STATUS` two-character codes checked after every I/O; `IF ACCTFILE-STATUS = '00' … ELSE DISPLAY … PERFORM 9910 … PERFORM 9999` | `io.*` throw `FileStatusException(ddname, operation, status)` with the ANSI codes the paragraphs test for (`10` EOF, `22` duplicate key, `23` not found, `30` permanent error, `35` missing file on OPEN, `39` record-length/attribute mismatch, `42` CLOSE/READ/WRITE when not open). Each paragraph catches it, stores the status in the same WORKING-STORAGE field the COBOL uses (`acctfileStatus`, …), and then follows the COBOL `IF` chain unchanged (DISPLAY, `displayIoStatus`, `abendProgram`). | Keeps the control flow of each paragraph a line-for-line match while giving Java callers a typed exception they can assert on. EOF is kept as a status (`Optional.empty()` → `10`) because the COBOL treats it as a normal branch, not an error. | The mapping from Java `IOException`s to codes is approximate (`30` for anything unexpected). |
| 10 | `9999-ABEND-PROGRAM`: `DISPLAY 'ABENDING PROGRAM'`, `MOVE 999 TO ABCODE`, `CALL 'CEE3ABD'` | `abendProgram()` displays the same line then throws `AbendException(999, 0, cause=FileStatusException)`; `main` catches it, prints `CEE3ABD: USER ABEND U999 TIMING=0` and exits with 999. `run()` returns 0 (RETURN-CODE) otherwise. | `CEE3ABD` never returns; an unchecked exception is the only honest Java equivalent. Carrying the triggering `FileStatusException` as the cause gives the operator the status and DD name the COBOL only DISPLAYs. | Exit code 999 is outside the 0–255 range a Unix shell shows (it becomes 231); the JCL/COBOL abend code is what callers of `run()` see. |
| 11 | `9910-DISPLAY-IO-STATUS` (`IO-STATUS NOT NUMERIC OR IO-STAT1 = '9'` → `NNNN` + stat1 + 3-digit binary of stat2, else `0000` + status in positions 3–4) | `displayIoStatus()` reproduces both branches: `FILE STATUS IS: NNNN0035` for a `35`, `NNNN9nnn` for a `9x` status. | Error-path DISPLAYs are part of the operational contract (operators grep for them). | The `9x` branch (`COMP` two-byte binary of the second status byte) is implemented but never produced by the Java I/O layer, so it is only unit tested indirectly. |
| 12 | `DISPLAY` of a group item / a numeric item | `FixedWidthRecord.display()` prints the record bytes as ISO-8859-1 text; `FixedWidth.display(field)` prints a zoned item as its digits followed by `+`/`-` (`000000019400+`), an unsigned item as its digits (`00000000001`), text as is. `PrintStream` is injected so tests capture stdout; `println` → `\n`. | GnuCOBOL (and the goldens) display a signed DISPLAY item as all digits plus a trailing sign, not with the over-punch character, and `DISPLAY ACCOUNT-RECORD` prints the raw 300 bytes (so the over-punch *does* appear there, e.g. `…1940{…`). Both are matched line for line in `display.txt`. | A `DISPLAY` of a COMP-3 item (not used by this program) would need `PackedDecimal`-aware formatting. |
| 13 | `CALL 'COBDATFT' USING CODATECN-REC` (assembler), type `'2'`, out-type `'2'` | `CobDatFt.call(CodatecnRec)` — a positional reformat with no parsing: copies input positions 1–4, 6–7, 9–10 to output positions 1–8. Also implements type `'1'`→`YYYY-MM-DD` and the `INVALID INPUT` error cases of the harness stub so the routine is complete. `CodatecnRec.setCodatecnOutDate(pos, text)` overwrites only the bytes written (an MVC), leaving bytes 9–20 untouched. | `MOVE CODATECN-0UT-DATE TO OUT-ACCT-REISSUE-DATE` moves X(20) → X(10): the result is `YYYYMMDD` plus bytes 9–10 of the 20-byte area, which are spaces because WORKING-STORAGE starts as spaces and the routine never writes them. A "parse and format" port would have produced `YYYYMMDD` + 2 spaces by accident; here it is by construction and pinned by `CobDatFtTest`. | Dates are never validated (`2025-13-45` would convert happily) — exactly as the assembler. |
| 14 | `IF ACCT-CURR-CYC-DEBIT EQUAL TO ZERO MOVE 2525.00 TO OUT-ACCT-CURR-CYC-DEBIT END-IF` with **no** `ELSE` and no `INITIALIZE OUT-ACCT-REC` | Same `if` without `else` on the storage-backed `OutAcctRec`, which the program constructor fills with **LOW-VALUES** (`lowValues()`) because it is an FD record area, not WORKING-STORAGE. | This is the surprising one: the output debit is *stateful*. A non-zero input keeps the previous record's output value; before the first zero input the field holds whatever the FD area contained — LOW-VALUES under GnuCOBOL (an invalid COMP-3 that the golden records as `INVALID-COMP-3:00000000000000`), undefined on z/OS. `golden-files/CBACT01C/synthetic-mixed-debit` pins inputs 10.00 / 0 / 120.50 / −75.25 / 0 → undefined / 2525.00 / 2525.00 / 2525.00 / 2525.00, and the Java reproduces it byte for byte. | **Business risk, not parity risk**: the "obvious" fix (`else` copy the input) would change the output on real data (the shipped 50 accounts all have a zero debit, so they would not reveal it). Fixing it is a product decision; see `TEST_STRATEGY.md` §7 and `CBACT01C-TOTAL-CYC-DEBIT` / `CBACT01C-FIELD-CYC-DEBIT`. On z/OS the first record's bytes would be whatever the buffer pool held. |
| 15 | `1400-POPUL-ARRAY-RECORD` constants `1005.00`, `1525.00`, `-1025.00`, `-2500.00` (`MOVE literal TO ARR-…(n)`) and `INITIALIZE ARR-ARRAY-REC` per record | `private static final BigDecimal` constants moved into occurrences 1–3 in the same order; `arrArrayRec.initialize()` before each record so occurrences 4–5 are zero. | Literal parity. `INITIALIZE` of a zoned item writes plain `000000000000` (no over-punch) while `MOVE 0` writes `…{` — the two zero encodings differ by a byte and the golden has the former in occurrences 4–5; `ZonedDecimal.initialize` therefore differs from `encode(0)`. | The constants look like test scaffolding left in a production program; they are reproduced, not questioned. |
| 16 | `VBRC-REC2.VB2-ACCT-REISSUE-YYYY ← WS-ACCT-REISSUE-YYYY` (`REDEFINES`-style split of `WS-ACCT-REISSUE-DATE` into YYYY / filler / MM / filler / DD) | `wsAcctReissueDate` string field, `wsAcctReissueYyyy()` = `substring(0, 4)` | The group/elementary split is a view over the same 10 bytes; a substring is the faithful equivalent. | None. |
| 17 | `INITIALIZE VBRC-REC1` before populating; `VBRC-REC2` not initialised | Same calls in the same places (`vbrcRec1.initialize()` only) | Every field of `VBRC-REC2` is assigned every record so the omission has no effect on the data; kept to mirror the paragraph. | None. |
| 18 | Output files never `CLOSE`d (only `9000-ACCTFILE-CLOSE`), `GOBACK` closes them implicitly | `run()` closes the three writers after `acctfileClose()` and before the final DISPLAY; a `finally` releases whatever is still open when the program abends | The runtime flushes/closes at `GOBACK` (and the step's allocations are freed on an abend); Java needs explicit `close()` to flush buffers. Order chosen so the DISPLAY stream stays identical. | None. |
| 19 | EBCDIC vs ASCII | The port is ASCII/ISO-8859-1 end to end and is validated against the **ASCII** sample data and the goldens generated from it. The EBCDIC originals in `app/data/EBCDIC` were only cross-checked by the safety net; no EBCDIC path exists in Java. | The goldens are the contract; adding an EBCDIC decoder without an EBCDIC golden would be untested code. Over-punch characters differ between code pages (`{`/`}` ASCII ↔ `C0`/`D0` EBCDIC), so a future EBCDIC reader needs its own `ZonedDecimal` table. | Reading real mainframe dumps requires a code-page step (e.g. IBM037) before `KsdsFile`. |
| 20 | `PERFORM UNTIL END-OF-FILE = 'Y' IF END-OF-FILE = 'N' …` with `APPL-RESULT` / `APPL-AOK` / `APPL-EOF` condition names | `while (!endOfFile)` plus the same `applResult` codes (0, 12, 16) kept as ints so the paragraphs read the same | The double EOF test in the COBOL loop is redundant; the Java keeps the semantics with one test. | None. |
| 21 | Line-sequential sample data vs the VSAM KSDS | `KsdsFile` tolerates an optional `\n` after each 300-byte record and rejects anything else (`39`) | `app/data/ASCII/acctdata.txt` is one record per line; the real dataset has no terminators. Handling both avoids a conversion step. | A record containing a real `0x0A` byte at position 300 is ambiguous (not possible for this copybook, which is all text/zoned). |
| 22 | Golden JSON shapes (`records.py`) | Test-side `JsonRecords` mirrors `records.py` (plain decimal strings, FILLER omitted, OCCURS as lists, `INVALID-COMP-3:<hex>` marker) so the Java output can be fed to `reconcile.py` unchanged | The reconciliation harness is the agreed judge; emitting its input format from the tests means the Python checks run on the Java output in CI (`ReconciliationTest.pythonHarnessAgrees`, skipped only if `python3` is missing). | None. |

## Things that were surprising

* **The `2525.00` rule is stateful** (#14). The port deliberately reproduces the legacy behaviour, including the
  LOW-VALUES first record of the synthetic fixture. Fix it only together with the fixture's expected rows.
* **Two different zero encodings** for the same `PIC S9(10)V99` field: `INITIALIZE` gives `000000000000`,
  `MOVE 0` gives `00000000000{` (#15). Both appear in the goldens.
* **`CODATECN-OUTTYPE` must be `'2'`** (the COBOL sets both type and out-type to `'2'`): type and out-type name
  the *input* format family, not "what I want out". A first draft of the port set out-type `'1'` ("I want
  YYYYMMDD") and wrote `2020250520` into `OUT-ACCT-REISSUE-DATE`; the byte diff against `raw/OUTFILE` caught it
  at offset 69.
* **`DISPLAY` of a numeric item** prints a trailing sign, while `DISPLAY` of the group record prints the raw
  over-punch byte — both in the same `display.txt`.
* **The golden `VBRCFILE` carries GnuCOBOL's 4-byte length prefix**, not an RDW; the program-level record
  lengths 12 and 39 are what the COBOL (and the port) control (#7).

## Not ported / out of scope

* `app/asm/COBDATFT.asm` itself (only its behaviour, as specified by `TEST_STRATEGY.md` and the harness stub).
* EBCDIC input (#19). JCL (`READACCT.jcl`) DD allocation is replaced by command-line paths.
